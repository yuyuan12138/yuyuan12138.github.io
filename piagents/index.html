PiAgents

One router conversation, dozens of AI workers — correctness from architecture, not model IQ.

PiAgents is a personal operating system that turns one conversation into a dispatcher and verifier. The router writes briefs, dispatches, and accepts; clean-context subagents do all the execution; every claim is re-checked against the filesystem before it counts. Everything is plain text — Markdown rules, role templates, vendored extensions, a few small scripts. No hidden binaries, no cloud dependency.

01 / How it works

The router dispatches. The workers execute. The tests decide.

Four subsystems, none of them trusting the others’ claims. The router never executes; the workers never persist; the acceptance tests never move; memory never promotes itself.

Zero inline execution

Router

The primary conversation never edits code. It understands requirements, writes briefs, dispatches, and accepts — where acceptance means running the tests and reading the diff itself, not reading a report.

9 role briefs · clean context · disposable

Workers

All execution happens in short-lived subagents: scout, planner, coder, operator, reviewer, researcher, visualizer, writer, designer. Each starts clean from a written brief and its own skill file, reports milestones as messages, and is rebuilt for the next task.

Best-of-N · fixed acceptance tests

Verification

Bounded work runs as N=3 candidates in isolated copies against identical, fixed acceptance tests — never weakened to make a candidate pass. A PASS report is a claim until it is re-checked against real files, logs, and git.

4 layers · human-approved gates

Memory

Session observations, a daily decision log, distilled concepts, and a sourced wiki — searched by an offline SQLite FTS5 index. A lesson goes global only with evidence from two projects and explicit user approval; unapproved content stays local.

03 / Field notes

Four incidents that became rules.

None of these were intelligence problems. They were the gap between what a system said it did and what it actually did — a gap no model upgrade closes.

26 failing tests

Blamed on the environment

A commit record called 26 failing tests “pre-existing environmental issues.” A baseline A/B on the same machine: restore the previous payload — 394 passed, 0 failed; add back one new file — exactly those 26 fail. The failure set moved with the file.

RuleA commit record’s test numbers are claims, not evidence — re-derive them.
465 requests · 53 lying receipts

The tool that lied 53 times

A game-playing run read “Dug stone, ok” 53 times while the server credited 1 stone. 72% of the run went to bare-hand mining with zero yield. The fix was not a smarter model — it was receipts that distinguish server_confirmed from client_predicted.

RuleWhen results look wrong, don’t upgrade the model — check whether the tools are lying.
0 commits in git

The worker that invented its homework

A subagent reported four completed episodes and a commit containing the results. git log had no such commit; the files were untouched. Acceptance changed: every claim is re-checked against git and the filesystem, and an adversarial checker exists to prove the first worker wrong.

RuleAcceptance is a git diff and a test run, not a read.
21 seconds

Death of an episode

The first fully automated A/B died 21 seconds in. The autopsy cleared the suspect: a known connection flake, then the episode’s own teardown stopped the server gracefully, exit 0. The driver’s own zombie-reaping bug surfaced on the way. Test count went from 57 to 84.

RuleReal systems bite back; the autopsy is part of the run.

The loop tunes the harness. The human keeps the gate.

The loop has run in observe mode only: it records “would accept” decisions, and live apply requires an explicit human flag. State checkpoints after every step; crashed experiments are never replayed. There is deliberately no auto-accept — acceptance is the human’s, at the gate.
