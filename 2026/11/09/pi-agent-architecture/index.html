One human, dozens of AI workers: my agent coordination architecture

A friend asked what my AI setup looks like, and the honest answer sounds strange: I don't really have "an AI assistant" anymore. I have a router conversation that never does the work itself, and behind it a rotating cast of dozens of short-lived workers. The router breaks my goal into bounded tasks, writes a brief for each, dispatches them, then verifies what comes back against the filesystem and git. It accepts or bounces. The engine underneath is Pi, an open-source coding agent harness, but the interesting part is not the engine — it is the operating discipline built on top of it: how work gets dispatched, why nothing is trusted on its own word, and what self-improvement looks like when the model never grades its own homework.

The router does no work

The core rule is blunt: the primary conversation is forbidden from executing tasks. If the primary can do it, a subagent can do it too. The primary's actual job is the part that cannot be delegated — understanding what I want, decomposing it, writing briefs, making decisions, and accepting or rejecting deliverables. Everything else — research, coding, testing, deployment, even "trivial" one-line fixes — goes to a worker.

Every worker starts from a clean context with a written brief. There are nine predefined roles, each just a folder of markdown: a brief template, a skills file the worker reads first, and a running record of lessons from past jobs. Scout maps a codebase without judging it. Coder implements minimally and reports in three states: implemented, tested, or unverified. Operator executes runbooks mechanically and never retries operations with unknown outcomes. Reviewer produces findings with file-and-line evidence but never edits. Researcher, planner, visualizer, writer, and designer fill in the rest. Each role also gets a tool allowlist — a reviewer can read but not write. These are workflow constraints rather than true sandboxes, so the real safety line is written into the brief: delegation never expands authorization.

The router keeps two dispatch channels. A fork inherits the entire live conversation — useful for debugging sessions where the context is the task, expensive because every forked turn re-reads the whole history. A subagent starts blank and gets only what the brief says — cheap, and the default. Long chains run in the background so the router never sits blocked; reports arrive as new messages while it moves on to the next dispatch.

Workers get things wrong, so claims don't count

This discipline was not designed on a whiteboard. Workers sometimes fabricate — confidently, plausibly, citing files that don't say what they claim. Once, a worker's commit record described 26 failing tests as "pre-existing environmental issues". I ran a baseline A/B on the same machine: restore the previous files, keep the tests identical, see whether the failure set moves with the change. It did. Not the environment — a regression. Nobody would have caught that by reading the report, because the report itself was the problem.

Acceptance means the router personally runs the tests, inspects the actual diff, and checks the deliverable. A green API response is not a working user journey.

The sharpest version of this rule comes from a side project: a Minecraft agent learning to craft a wooden sword through self-improvement. I refused to trust in-process flags or the model's narration. Success is defined as a counter in the game server's stored player data — crafted:wooden_sword ≥ 1 — read from the server, not from anything the model can touch. In one episode the model made 117 requests, and the server stats confirmed two swords. That number meant something precisely because the model had no path to it. The same pattern showed up in a web platform project: workers ran a load test that surfaced the real ceiling — about 500 concurrent users at 33 requests per second — plus three genuine bugs. What made those results acceptable was not the confident summary but the evidence trail anyone could re-check.

The shape of the system

Put it together and the architecture looks like this:

                        you
                         |  requirements, decisions, final acceptance
                         v
   +-----------------------------------------------------+
   |              coordinator conversation               |
   |    decompose -> brief -> dispatch -> verify ->      |
   |    accept or bounce        (never executes work)    |
   +------+-------------------------+--------------------+
          |                         |
        fork                  subagent x N
   inherits the live      clean context + role brief
   conversation branch    isolated worktree each
          |                         |
          v                         v
   one context-heavy      9 roles: scout / planner / coder /
   worker                 operator / reviewer / researcher /
          |               visualizer / writer / designer
          |                         |
          +------------+------------+
                       v
     acceptance: run the tests yourself, read the diff,
                 verify the evidence
                       |
        verified ------+------ bounced with reasons
                       v
     memory: raw streams -> observations -> curated
             knowledge base -> skills & rules
             (lessons pass a human-approved gate)

Nesting is capped — a worker may delegate once more, but no deeper — because unbounded chains of agents grading each other is how you lose track of reality.

Best of N

For bounded tasks with an objective verifier — a test suite, a live check — my default is not one worker but N, usually three, sometimes five. All N get the same brief, the same fixed acceptance tests, and their own isolated working copy of the repository. When they finish, the router verifies each candidate — runs the tests, reads the diff, checks the deliverable — and accepts the best, reporting every failure honestly.

This sounds wasteful. It is actually the cheapest insurance I know of. With fast parallel API capacity, three attempts at a well-specified task beat one attempt plus a debugging conversation — the candidates fail differently, and the fixed acceptance tests act as a common yardstick. The one rule I never bend: the criteria do not move. If no candidate passes, the failure gets diagnosed and one repair round follows; weakening a test to manufacture a pass corrupts the whole system. A recent security fix ran four parallel workers on their own git worktrees with disjoint files; the results merged cleanly and the full 438-test suite went green before anything was accepted.

Four layers of memory

Everything an agent session produces is worth keeping, but not everything is worth believing. My memory is layered by trust.

The bottom layer is the raw session stream — everything said and done, kept as-is. Above it sits observational memory: as a long session compacts, an observer writes short notes and reflections that can be recalled later. Useful, fallible — treated like a colleague's meeting notes, re-checkable against the original files.

The third layer is a curated markdown knowledge base, and this is where the discipline lives. After a verified result produces a transferable lesson, one entry goes into a daily log: context, the lesson, a source pointer. Recurring lessons get promoted into concept articles, and a compiler script regenerates the index while linting for broken links, missing metadata, and secret patterns. The interesting gate is scope: a lesson is project-scoped by default, and promoting it to global scope fails closed unless the evidence cites logs from at least two distinct projects and the approval field says "user-approved". A naive global memory pool performs worse than no memory at all. Every article also carries provenance — AI-generated or human-written, and a last-reviewed date.

The top layer is skills and rules: distilled procedures the agents load at dispatch time. Lessons survive across projects only by passing through that human gate.

The self-improvement loop

The Minecraft experiment ties all of this together, because there the agent has to improve itself, and self-deception is the failure mode to beat. The loop is: run an episode with the current skill library; check the server for the crafted-sword counter; if there is no sword, feed the episode summary — action sequences, failure codes, inventory changes — to the model and let it write a new skill; merge the skill into the library with deduplication and a hard cap of 48; reset the world and run again.

Two anchors keep the loop honest. First, server-authoritative evidence: only episodes verified by the server count as successes a skill may cite, and the model may propose skills but never judge them. Second, controlled experiments: when the loop stalled, I stripped terrain and navigation out with a superflat map and found the true weakness — the agent could mine a block but couldn't pick up the dropped item, walking off to search for a log that no longer existed. That is a model-capability finding, and no amount of optimistic self-reporting would have surfaced it. A background worker is running this loop automatically right now, reporting each round's server-verified result.

Why bother

The short answer: I am one person, and I want to operate at the scale of a team. The architecture is the point — not the model. The workers can be modest, self-hosted models, because correctness comes from the harness: briefs that bound the work, acceptance that checks reality, memory that only promotes what survived verification. A smarter model makes every worker better; it removes none of this, because the failure modes I designed around are not stupidity. They are the ordinary gap between what a system says it did and what it actually did.

None of this is exotic. The whole "kernel" is markdown rules, role templates, and a few hundred lines of scripts, plus a handful of small local extensions. The guards are best-effort, the memory is lossy, and every week some new incident teaches me another rule. The system is not trying to be impressive. It is trying to make one honest human and a few dozen fallible agents add up to more than either alone.
