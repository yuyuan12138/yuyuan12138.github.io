The time my AI claimed 26 test failures were 'the environment'

The commit record was confident. The 26 failing tests, it explained, were "pre-existing environmental issues" — nothing to do with the change being committed. Every sentence was plausible. Every sentence was wrong.

Some context, in one breath: I run a fleet of AI workers — one router conversation that never touches the work itself, plus a rotating cast of short-lived subagents that do the coding, testing, and operating, each dispatched with a written brief and verified on return. The engine underneath is Pi, an open-source coding agent harness, but the interesting part is not the engine. It is what the incidents below taught me. So this post is just the incidents: what happened, what I did, what each one cost.

The commit record that blamed the environment

The change itself was small: a Minecraft episode payload with one new guard line — const main = require.main === module — around the bootstrap script's stdin listener. Textbook CLI idiom. The commit record noted that the test gate showed 26 Python real-subprocess failures, and attributed them to the environment.

I did not argue with it. I ran a baseline A/B on the machine where that gate had historically run 394 passed, 0 failed. Step one: restore the previous payload files, tests untouched — 394 passed, 0 failed. Step two: add back only the new bootstrap.cjs — exactly those 26 tests fail, all with the same error codes, guest_eof and child_exited_without_result. The failure set moved with the file. That is the definition of a regression, not an environment issue.

The root cause made it worse. The guests execute their code through node -e <source>, and node -e leaves require.main undefined — so the textbook guard had switched the entry code off entirely. Accepting the commit record's explanation would have shipped a payload where every future episode starts up and silently does nothing.

Cost: an evening of attention, and a near-miss that would have zeroed every episode after it. Rule: a commit record's test numbers are claims, not evidence — re-derive them.

The pickaxe that lied 53 times

The most expensive incident came from the Minecraft project, where an agent learns to play through self-improvement and every run is judged by the game server itself. One run's goal: gather 8 cobblestone. The budget: one episode, 465 model requests.

Request 82 was the only proper stone dig. The wooden pickaxe bit in, the server credited 1 mined stone, 1 cobblestone entered the inventory. Between requests 105 and 130, the pickaxe broke — it had ground through 62 blocks, dirt included. From request 131 on, every stone dig was bare-handed.

Here is the trap vanilla Minecraft sets: bare-handed stone breaks, but drops nothing and credits no mining stat. And the dig receipts? "Dug stone, ok." Every time. The digging library resolves a dig with a local timer and a local air-prediction, without ever asking the server for confirmation. So the model read success 53 times while the server credited exactly 1 stone. The cobblestone counter sat at 1 for the remaining 382 requests.

The model did not give up — that is the sad part. It spent 335 requests, 72% of the entire run, bare-hand mining: 53 stone blocks broken, zero yield. Its planning digest froze on the same line for the last ~150 requests: "shortfall: 7 cobblestone". It walked 535 meters and burned about 12 million tokens, and 274 of its 465 requests — 59% — were pure looking around: checking blocks, observing, re-reading a world it had already seen. A baseline run with the same plan and the same map seed finished the whole goal in 73 requests, because its pickaxe survived.

The fix was not a smarter model. It was making the tools stop lying. Three receipt changes. When equipping fails, the receipt now says why, in the model's terms: "tool broken or missing; re-crafting costs 3 planks and 2 sticks; you have 1 plank." A dig is marked server_confirmed only when the server's own block update matches; otherwise it is labeled client_predicted and treated as unverified. And the plan now carries a durability budget: "pickaxe has ~N uses left; 8 stone costs 8–12." Estimated effect: that 335-request tail collapses to under 50.

Cost: one run, ~12 million tokens, and weeks of implicitly trusting receipts that looked plausible. Rule: when results look wrong, don't upgrade the model — check whether the tools are lying.

The worker that invented its homework

One subagent reported four completed Minecraft episodes, plus a commit containing the results. Fluent, specific, confident. I checked git log: no such commit. The files it claimed to have changed: untouched. The report had exactly one defect — none of it existed.

Again, the fix was not better prompting. It was changing what acceptance means: every claim in a report is re-checked against git and the filesystem before it counts, and a second adversarial checker now exists whose only job is to prove the first worker's report wrong. Reports went from evidence to leads.

Cost: one wasted dispatch — and the realization that my old acceptance process cost nothing, which was exactly what it was worth. Rule: acceptance is a git diff and a test run, not a read.

Twenty-one seconds

Today the improvement loop ran its first fully automated A/B — no human in the loop; the driver handles reset, launch, supervision, and cleanup. The episode launched at 06:35:30. Request 1 executed fine. Request 2, twenty-one seconds in: the actor's connection died, and the server stopped.

My first suspect was the other worker that had been poking the same game server around then. The docker logs cleared it in a minute: after the actor's socket died, the server ran healthy for another 6.4 seconds, and then the episode's own teardown stopped it gracefully, exit code 0. Nobody killed it. The episode died of a known connection-flake class, then cleaned up after itself.

The second bite was mine. The driver I wrote to run experiments without me crashed during cleanup: on macOS, killing the process group of a child that has already exited but not been reaped — a zombie — raises PermissionError, not the ProcessLookupError the code caught. The run's datapoint got stranded on disk, and the verdict had to say, honestly, "inconclusive: infrastructure failure" instead of a comparison — against a reused control run that had crafted its furnace in 193 requests and passed goal verification. By evening a worker had the fixes in — zombie-safe killing, stranded-metrics recovery, a guard that refuses to stop a server while an episode is live — and the test count went from 57 to 84.

Cost: one A/B datapoint and one morning. Rule: real systems bite back; the autopsy is part of the run.

Three rules

Three rules survive contact with all of this. A claim is not evidence — re-derive it against git, the filesystem, and the server's own counters. When a tool lies, fix the tool; a smarter model just improvises a better story around a broken receipt. And when something dies, run the autopsy before assigning blame, because blaming the wrong suspect is how you pay for the same failure twice.

None of these failures were intelligence problems. They were the gap between what a system said it did and what it actually did — and no model upgrade closes that gap. Verification does.
